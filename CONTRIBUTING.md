# Contributing to QCSS

Thanks for helping. QCSS is judged by one question: *can a quantum OS talk to it exactly as it talks
to hardware, and trust the answers?* Contributions are welcome when they move that forward and stay
honest about what is verified and what is not.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). Contributions are licensed
under the project's [Apache-2.0 license](LICENSE).

## Set up

```bash
git clone https://github.com/PratulDeshpande/qcss.git
cd qcss
uv sync --group dev                              # Python 3.12 or 3.13: the simulator and the dev tools
uv sync --extra qibocal --extra qick --group lab --group dev  # plus the virtual lab and the native QICK face
uv pip install "qibosoq @ git+https://github.com/qiboteam/qibosoq@2c376278785e6ae8aae1f13d1b0b467e067aaf7d"
uv pip install "qick==0.2.370"
```

The `uv pip install` lines are only needed for the board tests. qibosoq has no numpy-2 release on PyPI,
and a git dependency cannot be declared in the package metadata; the `qick` client is installed by hand
because its `pynq` dependency (for the board's ARM CPU) cannot be resolved in uv's universal lock. Run
them again after any `uv sync`, which removes packages the lock does not list. Without the lab stack the
`virtual_lab`, technician and platform tests skip; without Pyro4 and `qick` the QICK face's tests skip.

## Checks to run before opening a pull request

```bash
python -m pytest -n 2                  # must pass (keep -n low on a laptop: the physics tests use a lot of memory)
ruff check .                           # must be clean
pyright                                # must report 0 errors (run it in the lab venv, so qibolab and qibocal resolve)
python scripts/gen_proto.py            # only if you edited a .proto file (instrument link or admin channel)
```

CI runs the same checks: lint, type check against the lab stack, generated-code freshness, the test
suite on Linux and Windows (Python 3.12 and 3.13), and a `virtual-lab` job that installs Qibolab,
Qibocal and the qibosoq pin and runs the whole suite. The proto job regenerates the protobuf code and
fails if the committed files in `src/qcss/v1/` differ, so commit regenerated code together with the
`.proto` change. (The admin stubs in `src/qcss/admin/v1/` are regenerated by the same script but not
yet diffed in CI; check them yourself.)

> **Typing tips.** Some third-party stubs are stricter than the libraries. Prefer `np.real(x)` /
> `np.imag(x)` over `x.real` / `x.imag` on loosely typed arrays, and `@` (not `*`) for qutip operator
> products. Keep `# pyright: ignore[rule]` for genuine upstream stub bugs, with a comment saying why.

## Ground rules

* **The `.proto` files are the product.** Changes must keep `buf lint` (STANDARD) clean and must not
  break the wire format (`buf breaking`, WIRE_JSON). Every enum keeps `*_UNSPECIFIED = 0`.
* **Hardware numbers are data with a source.** A new or changed profile value needs a `provenance`
  block (`source_url`, `firmware_version` where known, `verified`). If you cannot source it, mark it
  `verified: false`. Never hard-code a vendor constant in Python.
* **Each error enters exactly once.** Decoherence enters through the physics engine, readout error
  through the readout model, drift through the device state. Double counting produces results that
  look plausible and are wrong.
* **Refuse, don't approximate.** If a tier cannot honour a job, the router refuses with a reason; it
  never silently runs a cheaper model.
* **Time is an integer number of ticks.** Convert to nanoseconds only at API edges.
* **Randomness is keyed, not global.** Draw from `qcss.core.seeding.stream(...)`; never use Python's
  `hash()` or an unseeded generator, or seeded jobs stop reproducing. The chassis seeds from entropy
  by default (a lab never repeats); replay is for `qcss run` and `--deterministic` only.
* **The lab link must not give the simulator away.** Nothing a lab client can reach (instrument link,
  board face, platform files, results, error text) may carry a tier, a noise fidelity, the true chip
  parameters, a simulator class name or a seed. Simulator-only knobs and diagnostics go on the admin
  channel (`proto/qcss/admin/v1`). `tests/integration/test_indistinguishability.py` enforces this.
* **QCSS never writes calibration.** The platforms' `parameters.json` and `calibration.json` are written
  by Qibocal (the technician) only; the Qibolab driver reads them and uploads settings per `play`.

## Tests

Tests are the specification. New physics comes with an analytic oracle (a closed-form result compared
within a stated statistical tolerance, such as 5σ binomial), not a number copied from a run.

| Directory | What it holds |
|---|---|
| `tests/unit/` | One file per module, plus Hypothesis property tests |
| `tests/oracles/` | Physics compared with analytic formulas through the real runtime |
| `tests/cross_tier/` | Tiers agree where their domains overlap |
| `tests/integration/` | gRPC end to end, chassis, admin channel, board face, technician, indistinguishability |
| `tests/virtual_lab/` | Acceptance through the path Quark takes (QASM in, Qibolab compile, counts out); marker `virtual_lab` |
| `integrations/qcss_qibolab/tests/` | The Qibolab driver: translation, platforms, calibration pinning |

Use the `stochastic` and `slow` markers for statistical and long-running tests, and `virtual_lab` for
tests that run through Qibolab against a chassis. Do not hard-code network ports: bind to port 0 or use
the `_free_port()` helper in the gRPC tests. A test that asserts physics against a chassis should pin
the chip with `TEST_CHIP_SEED` (see `tests/integration/test_admin_cli.py`): with fresh entropy about one
start in twenty puts a TLS defect on a qubit, and the test would fail by luck.

## Style

* `ruff` with the settings in `pyproject.toml` (line length 120). Generated `*_pb2*` files are excluded.
* Match the surrounding code's naming and comment density. Comments explain *why*, not what.
* Keep pull requests focused: one concern per PR, with a description of what changed and how you
  checked it.

## Reporting bugs and requesting features

Use the issue templates. For a bug, a minimal job file and the exact command are the most useful
things you can include. For security problems, see [SECURITY.md](SECURITY.md) and do not open a public
issue.
